# 需求功能参考实现生成

本 skill 负责：
1. 阅读用户给出的功能需求描述。
2. 在 AFSIM 中查找与需求描述相关的参考实现。
3. 根据AFSIM实现逻辑，形成结构化的参考程序设计文档。
4. **重点**：每个用户需求独立，禁止阅读其他用户需求的内容，禁止将其他用户需求的内容作为参考依据。

## 输入

- AFSIM：
  - 代码架构文档(docs/architecture/*.md)
  - 代码索引(workspace/source-index/*.jsonl)
  - 算法文档(docs/algorithms/*.md)
  - 演示参考(source-root/afsim-2.9/demos/<demo_name>/*.txt + README.md)
  - 使用文档(source-root/afsim-2.9/documentation/*)
- 用户：
  - 功能需求描述
  - 可依据的其他文献

## 执行步骤

0. 预处理：
  - 确认用户提供的功能需求描述是否明确，若不明确则人工确认。
  - 确认是否有需求编号，若没有则人工确认。
  - 确认是否有可依据的其他文献，若没有则人工确认。
  - 确认是否有 AFSIM 侧输入（代码架构文档、代码索引、算法文档、演示参考、使用文档），若没有则人工确认。
  - 确认用户提供的功能需求描述是否与 AFSIM 代码架构文档、代码索引、算法文档、演示参考、使用文档等已有认知一致，若不一致则人工确认。

1. 加载上下文：
  - 读取 AFSIM 架构报告（docs/architecture/afsim-architecture.md）
  - 读取算法卡片概览（docs/algorithms/CompendiumofAlgorithms.md）
  - 加载 AFSIM 源码功能索引（workspace/source-index/function-index.jsonl）
  - 加载 AFSIM 使用文档总览（source-root/afsim-2.9/documentation/index.html）

2. 解析用户模糊的功能需求：
  - 读取用户提供的功能需求描述
  - 提取文档结构和关键领域词
  - 解析用户自然语言，将模糊表述拆解为可判断的功能陈述。
  - 按照系统-模块-类级-方法的层级结构，判断功能类别：
    - 判断功能所属系统
    - 判断功能所属模块
    - 判断功能所属类级
    - 判断功能所属方法

3. 将需求拆分为算法流水线:
  - 对于拆解后的每条功能陈述，在 AFSIM 源码功能索引`function-index.jsonl`中通过语义搜索找到最相关的函数或类。
    - 若找到匹配：评估匹配函数的接口、依赖、输入输出。
      - 注意：不可仅依赖 `function-index.jsonl` 的函数名和简要描述来判断匹配度，必须打开对应的源码文件逐行阅读，确认输入输出、依赖关系和功能实现。
    - 记录候选函数的证据（路径、函数名、行号、功能摘要）。
  - 对于拆解后的每条功能陈述，在 AFSIM 算法卡片概览`CompendiumofAlgorithms.md`中通过语义搜索找到最相关的函数或类。
    - 若找到匹配：评估匹配函数的接口、依赖、输入输出。
      - 注意：不可仅依赖 `CompendiumofAlgorithms.md` 的一句话摘要替代卡片正文。若在CompendiumofAlgorithms.md中找到需求涉及的各 AFSIM 参考算法，必须打开对应的完整算法卡片（`docs/algorithms/*.md`）逐张阅读。
    - 记录候选功能的证据（算法卡片路径、名称、摘要）。
  - 对于拆解后仍然较为复杂的功能陈述，在 AFSIM 使用文档目录中通过语义搜索找到最相关的使用文档。
    - 若找到匹配：阅读该使用文档的内容，形成功能需求的详细描述。
      - 注意：不可仅依赖使用文档中的一句话摘要替代完整功能陈述，若在文档中找到其他文件的名称、链接、网址，必须打开对应的文件逐页阅读。
      - 注意：涉及到.txt文件的内容，需要判断功能涉及到的演示参考目录下的子目录，逐行阅读子目录下的README.md和.txt文件。
    - 记录候选功能的证据（使用文档路径、名称、摘要、演示文档路径、名称、摘要）。
  
  - **若仍未找到匹配**：标记为 🆕 AFSIM 无参考实现，该需求的算法流程需从领域文献或算法教材中寻找设计依据，不可依赖 AFSIM 源码。

4. 生成结构化参考程序设计：<需求标题>-reference.md

5. 等待人工确认：
  - 将生成的结构化需求草稿（docs/requirements/<requirement_index>/<需求标题>-reference.md）交给人工确认。
  - 人工确认是否有其他修改要求
  - 按照修改要求修改结构化需求草稿，直到人工确认无误。
    
4. 过程留痕：把每一步的决策依据和执行计划生成文档进行记录归档，放在目录docs/records里面，以便人工追溯。
